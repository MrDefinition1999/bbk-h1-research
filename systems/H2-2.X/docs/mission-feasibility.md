# “使命”移植到 H2 V2.2L 的结论

## 当前总览

本项目现有两条必须分开描述的实验分支：

- **2026-08-26，H1 V1 使命负载**：能从 H2 原生桌面启动并显示主菜单、创建角色和剧情，但进入“光明城”任务场景后画面不完整。堆探针确认场景切换期间发生真实内存分配失败。这是仍然有效的历史阶段性结果。
- **2026-08-27，S1 原版使命负载**：当前活动镜像。stage 已加载精确 S1 原版 BDA 并进入 `game-start`，H2 原生 shell handle 非零，但可见前台仍是词典 UI。这个分支尚未显示使命首窗，当前阻塞点是前台/窗口 ABI，不是已经证明的内存不足。

两条分支都没有达到 H2 可玩结论。下面的内存、32 位画面接管和任务场景数据专指 H1 V1 负载分支；“S1 原版跟进状态”一节描述当前实验。

这不是把 H1 模拟器或 H1 固件复制到 H2。H2 运行时只包含 H2 V2.2L 固件、JZ4750L/H2 设备模型和 H2 专用包装层。H1 两套模拟器及其文档只用于复用以下方法经验：V1 ABI 前缀构造、服务槽映射、应用内存接管、跟踪记录和退出恢复。共享的通用 ABI 映射是源码级组件，不包含 H1 机器镜像。

验证结论还必须区分模拟器和实机：

- ARM64 H2 模拟器：基础系统已验证；H1 负载有菜单/剧情结果，S1 原版负载仍卡在可见首窗之前。
- 真实 H2：尚未跑通。模拟器保持与实机一致的 32 MiB RAM，不允许用虚增内存掩盖问题。

## H1 V1 负载的 H2 专用实现

H2 原生 BDA 前缀位于 `0x81C30000`，应用入口为 `0x81C30040`；32 MiB SDRAM 的回绕别名为 `0x83C30000`。H1 V1 游戏固定从 `0x83C00020` 进入，因此 H2 包装层执行以下操作：

1. 保存 H2 原生服务前缀和堆元数据。
2. 把 H2 的高端堆记录区从 `0x81C30000` 下移到 `0x81C00000` 以下，避免与 V1 负载别名重叠。
3. 在 `0x83E00000` 建立 V1 形状的兼容服务表，在 `0x83F00000` 运行 H2 stage。
4. 使命运行期间把 H2 LCD 前景层从原生 RGB565 切到游戏实际输出的 32 位 BGRA；返回时恢复原生 16 位桌面模式。
5. 使用 H2 GUI `+0x740` 的原生消息泵实现使命所需的 V1 GUI `+0x854` 边界。

已经验证包装层、V1GAME 负载、`DataLib.dat` 和 `DataLibIndex.dat` 均能从修改后的 H2 FAT 分区逐字节回读一致。最终包装层 SHA-256 为 `6825AC0DE56EBC66F71A8F6BAA5DB27D7873E0767A8871D19AEADE8EDCAE747C`；此摘要也记录在最终安装 manifest 中。

## RAM 实测与失败证据

H2 这一版实机只有 32 MiB SDRAM；超过 32 MiB 的地址会回绕到低地址。模拟器也固定为相同容量，没有增加 RAM。H2 系统初始化后留给通用分配器的池并非完整 32 MiB；使命包装层避开 V1 负载别名后，可用主堆为 `0x809EC000..0x81C00000`，共 `18,956,288` 字节（18.078 MiB）。

同一堆记录格式下的只读快照如下。数值是“整个系统主堆”的存活分配，不等于使命程序单独占用：

| 环境与时点 | 堆容量 | 存活分配 | 当时最大连续可申请 |
| --- | ---: | ---: | ---: |
| H1 1.X 原版，使命主菜单 | 32.000 MiB | 9.937 MiB | 22.040 MiB |
| H1 1.X 原版，实际任务场景 | 32.000 MiB | 20.023 MiB | 10.408 MiB |
| H2 2.2，启动使命前 | 18.266 MiB | 8.044 MiB | 10.023 MiB |
| H2 2.2，使命主菜单 | 18.078 MiB | 12.275 MiB | 5.434 MiB |
| H2 2.2，异常任务场景 | 18.078 MiB | 17.337 MiB | 0.366 MiB |

异常场景快照中的空闲记录与尾部合计约 0.739 MiB，但已经碎片化。更关键的是，从冷启动使命到任务场景的动态断点在 H2 内部分配器 `0x80025868` 命中了真正的失败分支，随后该函数返回空指针；该次命中时请求寄存器值为 `0xD8`（216 字节）。失败发生在瞬时峰值，事后快照出现可复用块并不否定它。

因此结论不是“使命需要 64 MiB”，而是原版完整任务场景在 H1 主堆中达到约 20.02 MiB 存活分配，而当前 H2 包装后只有 18.08 MiB 的主堆并在切换峰值发生分配失败。后续方向是在 32 MiB 物理边界内回收 H2 桌面资源、减少 32 位画面接管的额外占用或为使命安排不冲突的专用区；不得提高模拟器 RAM。

## S1 原版跟进状态（当前活动配置）

用户要求不再把 `BBK9588-shiming` 的 9588 兼容版当作 H2 游戏负载，也不要切回已经证明会在任务场景内存失败的 H1 负载。当前只测试该项目保存的 654,696 字节 S1 原版使命 BDA；9588 兼容版仅作为 GUI/字体 shim 的逆向参考。

对 60 个 H2 原生 BDA 的扫描证明 `GUI+0x980` 会打开各应用的 `A:\系统\数据\shell\*.dlx`，`GUI+0x990` 关闭返回的句柄；较早怀疑的 `GUI+0x018` 只是日志。当前 wrapper 复用 `TIME_Z.dlx`，运行 trace 得到非零 shell handle `0x81229EC0`，并进入 `game-start`。因此文件缺失、错误游戏负载、导航失败和缺少 H2 shell 上下文都已排除。

最终画面仍是正常词典 UI，QEMU 没有崩溃或重启。正确结论是 S1 游戏代码在后台/隐藏状态运行，尚未取得 H2 前台窗口所有权。最值得继续核对的是 S1 `GUI+0x084` 的 320×240 窗口描述符与当前映射目标 H2 `GUI+0x07C` 的结构和语义；创建出对象不等于完成前台注册。

S1 的实际 RAM 峰值尚未测得。它可能比 H1 版本小，但在首窗可见之前不能宣称 S1 已解决 H2 的内存边界。当前最后一层可由 `work/h2/s1-resource-test/undo-s1-original-shellctx.sectors.gz` 精确恢复到 `F60285BAE3081B2A694637F8EB63536D0A102080F8666E43BCECBC93951E7CAB`；完整回滚链见仓库根目录 `docs/22-current-project-handoff.md`。

## 七键输入

H2 没有 H1 全键盘。使命运行时采用以下上下文映射，退出后 H2 按键立即恢复原生含义：

| H2 实体键 | H2 消息 | 使命内含义 |
| --- | --- | --- |
| 左 | PC1，扫描值 `0x69` | 左 |
| 右 | PC3，扫描值 `0x6A` | 右 |
| 确认 | 原始 CR `0x0A` | 确认，按下值 `0x1C` |
| 返回 | 原始 Esc `0x1B` | 使命全局返回/退出事件 |
| 音量－ | 扫描值 `0x3D` | 下，扫描值 `0x6C` |
| 音量＋ | 扫描值 `0x3C` | 上，扫描值 `0x67` |
| 电源 | H2 系统电源路径 | 不改造成游戏键 |

OpenNoah 的 H2 设备模型在外来 V1 事件循环中偶尔丢失 PC1/PC3 的中断唤醒。网页控制器会为左右键附加一个可用的音量 IRQ 脉冲，H2 stage 读取真实 PC1/PC3 电平并吞掉该脉冲。这个兼容分支只在检测到模拟器镜像的 WAIT→NOP 标记时启用；真实 H2 保持原生音量键行为。

## 模拟器限制与修正

参考文章提供的 QEMU 没有完整实现 JZ4750L 从 `WAIT` 低功耗状态唤醒。原系统运行约一分钟后会停在 `0x804C49BC`，表现为黑屏、按键失效或重启后网页看似打不开。

`tooling/patch_h2_simulator_idle.py` 只对模拟器的两个系统副本执行可逆的单指令 WAIT→NOP 修正，并记录精确撤销日志。物理 H2 镜像和 H2 专用包装层不会删除真实硬件的低功耗逻辑。固定地址 `http://127.0.0.1:8797/` 的页面还会在 QEMU 重启、WebSocket 端口变化后自动重连。

## 联机功能

H2 没有 H1 的联机芯片。移植不创建虚假的联机设备，也不把联机入口伪装成可用。当前验证的“使命”路径是单机新任务；没有观察到该路径依赖联机硬件。

## H1 V1 分支已验证项与全局剩余工作

已在 ARM64 模拟器验证：

- H2 原生冷启动、桌面和触摸输入；
- 使命启动、主菜单、创建角色和剧情；
- 确认、左右、音量映射的按下/释放消息；
- 模拟器辅助唤醒事件不会泄漏为游戏方向；
- LCD 32 位接管和 H2 原生模式恢复；
- H2 堆记录区的迁移与恢复；
- WAIT 修正后超过原故障时间窗仍保持响应；
- 8797 页面在停止/启动后自动重连。

当前活动 S1 分支的首要工作是解决首窗/前台 ABI；只有使命画面真正可见后才继续测 S1 的 32 MiB RAM 峰值。若回到 H1 V1 分支，则首要工作仍是在 32 MiB 上消除任务场景分配失败。两个分支之后都需要真实 H2 完成实体 GPIO 手感、音频、存档/读档、长时间游戏和完整退出路径回归。源代码交付不包含厂商固件或游戏数据。
